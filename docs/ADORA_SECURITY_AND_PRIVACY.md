## 1. Threat Modeling & Attack Surfaces

Adora AI handles sensitive personal reflections, private life experiences, and agentic integrations capable of executing external actions. The security model addresses seven primary threat vectors:

### 1.1 Threat Matrix & Countermeasures

| Threat Vector | Description | Severity | Countermeasure |
|---------------|-------------|----------|----------------|
| **Cross-User Data Leakage (IDOR)** | Malicious user crafts requests with another user's `userId`. | Critical | Strict path partitioning under `/users/{request.auth.uid}/...` enforced by both server middleware and Firestore security rules. Server verifies Firebase ID token directly via Admin SDK; never trusts client-supplied UID. |
| **Prompt Injection into Agent** | Reflection content or external email containing prompt injection trying to execute unauthorized tools. | High | Strict structural schema validation on tool inputs via Zod. Mandatory human-in-the-loop approval gates for all Tier 2 consequential actions. Prompt isolation separating instructions from raw context strings. |
| **Unauthorized Consequential Execution** | Agent or rogue client attempting to bypass approval and send messages or mutate data. | Critical | Backend state machine enforces that a task cannot transition to `RUNNING` unless status was already `APPROVED` with valid user signature and timestamp. |
| **Client-Side Secret Exposure** | Leakage of `NEBIUS_API_KEY` or `GEMINI_API_KEY` in frontend bundle. | Critical | API keys are declared strictly as server-side environment variables. Vite config and bundling pipelines contain zero client-exposed keys. All LLM calls pass through server routes (`/api/v1/*`). |
| **Resource Exhaustion ("Denial of Wallet")** | Malicious client flooding server with massive text inputs or rapid-fire LLM requests. | High | Volumetric limits (max 10,000 chars per reflection), rate limiting on `/api/v1/*` routes, input string size checks in Firestore security rules. |
| **Unverified Action Hallucination** | Agent reporting a task completed when the API failed or was mocked. | High | Independent verification subsystem: read-back API query is required before state transition to `VERIFIED`. Execution receipts with SHA-256 payload digests. |
| **PII & Private Data Persistence** | Personal identity data exposed in multi-tenant search. | High | Split-collection isolation. Vector embeddings are isolated per user namespace and only queried against documents where `userId == request.auth.uid`. |

## 2. Authentication & Authorization Architecture

### 2.1 Authoritative Server-Side Token Verification
The server runs an authentication middleware on all protected API routes:

```typescript
import { auth as adminAuth } from './firebaseAdmin';

export async function requireAuth(req: Request, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ success: false, error: { code: 'UNAUTHENTICATED', message: 'Missing token' } });
  }

  const idToken = authHeader.split('Bearer ')[1];
  try {
    const decodedToken = await adminAuth.verifyIdToken(idToken);
    req.user = { uid: decodedToken.uid, email: decodedToken.email };
    next();
  } catch (err) {
    return res.status(401).json({ success: false, error: { code: 'INVALID_TOKEN', message: 'Token verification failed' } });
  }
}
```

### 2.2 Firestore Zero-Trust Rules Architecture
The Firestore security rules implement the Eight Pillars of Hardened Rules:
1. Default-deny catch-all at root: `match /{document=**} { allow read, write: if false; }`.
2. Master Gate: Documents under `/users/{userId}` can only be accessed if `request.auth.uid == userId`.
3. Validation helpers (`isValidReflection`, `isValidMemory`, `isValidTask`) assert field presence, data types, and character length bounds (`.size() <= MAX`).
4. Immutability checks: `incoming().createdAt == existing().createdAt` and `incoming().userId == request.auth.uid`.
5. Action-based update guards using `incoming().diff(existing()).affectedKeys().hasOnly([...])`.

## 3. Privacy & User Data Sovereignty

### 3.1 Non-Diagnostic Epistemic Guarantee
- Inferences generated by NVIDIA Nemotron are explicitly labeled as hypotheses.
- The UI visually separates verbatim user input from machine inference with distinct styling and provenance chips.
- Users can reject or delete any inference without degrading system integrity.

### 3.2 Complete Deletion Cascade
- When a user deletes a reflection:
  1. The reflection document is deleted from Firestore.
  2. Any unconfirmed candidate memories pointing exclusively to this reflection are deleted.
  3. Corresponding graph nodes and edges in Reflection Grove are pruned.
  4. Vector embeddings are purged from the nearest-neighbor index.

### 3.3 "Download My Vault" & Account Purge
- Users have on-demand capability to export all their reflections, memories, insights, and graph structures into a clean JSON/Markdown archive.
- Permanent account purge removes all collections under `/users/{userId}` in an atomic server-side batch.
